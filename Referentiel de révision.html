🔷 2. C# — Langage & Fonctionnement

2.1 Syntaxe & Bases

Syntaxe C# Core

Langage orienté objet, typé statiquement, développé par Microsoft. Points clés :

  • Types valeur vs référence : struct, int, bool (valeur) vs class, string, object (référence).
  • Nullables : int?, string?, opérateurs ?., ??, ??=.
  • Propriétés : auto-properties, expression-bodied members, init, required.
  • Pattern matching : is, switch expressions, when.
  • Records : types immuables avec égalité structurelle.

2.2 Fonctionnement interne

🗑️ GC (Garbage Collector)
  • Gère automatiquement la mémoire
  • 3 générations (0, 1, 2) + LOH
  • Libère les objets non référencés
  • Modes : Workstation / Server
  • IDisposable pour ressources non managées
⚙️ IL (Intermediate Language)
  • Code compilé par le compilateur C#
  • Indépendant de la plateforme
  • Stocké dans les assemblies (.dll, .exe)
  • Lu par le CLR (Common Language Runtime)
🔥 JIT (Just-In-Time)
  • Compile l'IL en code machine à l'exécution
  • Optimisé pour la plateforme cible
  • Compilation à la volée (méthode par méthode)
  • Avantages : optimisation runtime
🚀 AOT (Ahead-Of-Time)
  • Compilation native avant exécution
  • Pas de JIT au runtime
  • Démarrage plus rapide
  • Idéal pour containers, mobile, IoT
  • Native AOT en .NET 7+
// Exemple : GC et IDisposable
public class ResourceHolder : IDisposable
{
    private bool _disposed = false;

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (!_disposed)
        {
            if (disposing) { /* libérer ressources managées */ }
            // libérer ressources non managées
            _disposed = true;
        }
    }
}

📦 4. Collections .NET

Les collections sont des structures de données pour stocker et manipuler des groupes d'objets. Voici les principales :

4.1 Collections génériques (System.Collections.Generic)

Collection Description Accès Cas d'usage
List<T> Tableau dynamique redimensionnable Index O(1) Collection ordonnée, accès rapide par index
Dictionary<K,V> Table de hachage clé-valeur Clé O(1) Recherche rapide par clé unique
HashSet<T> Ensemble sans doublons O(1) Opérations ensemblistes (union, intersection)
Queue<T> File FIFO (First In, First Out) Enqueue/Dequeue O(1) Traitement dans l'ordre d'arrivée
Stack<T> Pile LIFO (Last In, First Out) Push/Pop O(1) Annulation, parcours en profondeur
LinkedList<T> Liste doublement chaînée O(n) index, O(1) insertion Insertions/suppressions fréquentes
SortedList<K,V> Dictionnaire trié par clé O(log n) Données triées avec accès par clé
SortedSet<T> Ensemble trié O(log n) Ensemble ordonné sans doublons
ConcurrentDictionary<K,V> Dictionnaire thread-safe O(1) Accès concurrent multi-thread

4.2 Différences clés

List vs LinkedList
  • List : accès indexé rapide, insertion lente au milieu
  • LinkedList : insertion rapide, accès indexé lent
  • List = tableau dynamique
  • LinkedList = nœuds chaînés
Dictionary vs HashSet
  • Dictionary : clé → valeur
  • HashSet : uniquement des valeurs uniques
  • Dictionary pour lookup par clé
  • HashSet pour tests d'appartenance
Queue vs Stack
  • Queue : FIFO (premier entré, premier sorti)
  • Stack : LIFO (dernier entré, premier sorti)
  • Queue = file d'attente
  • Stack = pile d'assiettes
Array vs List
  • Array : taille fixe, plus performant
  • List : taille dynamique, plus flexible
  • Array pour taille connue
  • List pour taille variable
// Exemples d'utilisation
var list = new List<int> { 1, 2, 3 };
var dict = new Dictionary<string, int> { ["a"] = 1, ["b"] = 2 };
var set = new HashSet<int> { 1, 2, 3 };
var queue = new Queue<string>();
queue.Enqueue("premier");
var stack = new Stack<string>();
stack.Push("dernier");

// LINQ sur collections
var evens = list.Where(x => x % 2 == 0).ToList();
var sorted = dict.OrderBy(kv => kv.Value).ToList();

🔗 5. LINQ & Sérialisation

5.1 LINQ (Language Integrated Query)

LINQ Core

Permet d'interroger des collections, bases de données, XML, etc. avec une syntaxe unifiée.

  • LINQ to Objects : collections en mémoire
  • LINQ to SQL / EF : bases de données
  • LINQ to XML : documents XML
  • Syntaxe : méthode (fluent) ou requête (query)
  • Deferred execution : exécution différée
// Syntaxe méthode
var result = users
    .Where(u => u.Age > 18)
    .OrderBy(u => u.Name)
    .Select(u => new { u.Name, u.Email })
    .ToList();

// Syntaxe requête
var result2 = from u in users
              where u.Age > 18
              orderby u.Name
              select new { u.Name, u.Email };

// Opérateurs courants
// Where, Select, OrderBy, GroupBy, Join, Any, All, First, Single
// Aggregate, Sum, Count, Distinct, Union, Intersect, Except

⚡ 6. Asynchronisme & I/O

async / await Core

Mécanisme pour exécuter des opérations longues (I/O, réseau, base de données) sans bloquer le thread principal.

  • async : marque une méthode comme asynchrone
  • await : suspend l'exécution sans bloquer le thread
  • Task, Task<T>, ValueTask
  • Bonnes pratiques : async all the way, éviter async void, ConfigureAwait(false)
// Appel asynchrone
public async Task<User> GetUserAsync(int id)
{
    var response = await _httpClient.GetAsync($"/api/users/{id}");
    response.EnsureSuccessStatusCode();
    var json = await response.Content.ReadAsStringAsync();
    return JsonSerializer.Deserialize<User>(json);
}

// Exécution parallèle
var tasks = ids.Select(id => GetUserAsync(id));
var users = await Task.WhenAll(tasks);

🧭 7. Principes de Développement

S — Single Responsibility
  • Une classe = une seule responsabilité
  • Une seule raison de changer
  • Facilite la maintenance
O — Open/Closed
  • Ouvert à l'extension
  • Fermé à la modification
  • Utiliser interfaces/abstraction
L — Liskov Substitution
  • Une sous-classe doit pouvoir remplacer sa classe parente
  • Pas de comportement inattendu
I — Interface Segregation
  • Interfaces spécifiques plutôt que générales
  • Pas de méthodes non utilisées
D — Dependency Inversion
  • Dépendre des abstractions, pas des implémentations
  • Injection de dépendances
YAGNI
  • You Aren't Gonna Need It
  • Ne pas anticiper des besoins hypothétiques
  • Implémenter quand c'est nécessaire
KISS
  • Keep It Simple, Stupid
  • La simplicité avant tout
  • Éviter la sur-ingénierie
DRY
  • Don't Repeat Yourself
  • Éviter la duplication de code
  • Factoriser les logiques communes

🌐 9. ASP.NET & API

9.1 API : MVC vs Minimal API

MVC / Web API (Controllers)
  • Structure en contrôleurs
  • Attributs de routage
  • Idéal pour grosses applications
  • Filtres, conventions
  • Exemple : [ApiController]
Minimal API
  • Moins de code, plus direct
  • Idéal pour microservices
  • Pas de contrôleurs
  • Lambdas dans Program.cs
  • Exemple : app.MapGet("/", () => "Hello");

9.2 Concepts clés

Routing

Définit comment les URLs sont mappées aux actions. Attributs : [Route], [HttpGet], [HttpPost], etc.

Middleware

Pipeline de traitement des requêtes HTTP. Chaque middleware peut :

  • Traiter la requête
  • Passer au middleware suivant (next())
  • Court-circuiter la pipeline
Injection de dépendances (DI)

Principe d'inversion de contrôle. Cycles de vie :

  • Transient : nouvelle instance à chaque demande
  • Scoped : une instance par requête HTTP
  • Singleton : une instance pour toute l'application
// Minimal API
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddScoped<IUserService, UserService>();
var app = builder.Build();

app.MapGet("/users/{id}", async (int id, IUserService service) =>
    await service.GetUserAsync(id));

app.Run();

// Contrôleur MVC
[ApiController]
[Route("api/[controller]")]
public class UsersController : ControllerBase
{
    private readonly IUserService _service;
    public UsersController(IUserService service) => _service = service;

    [HttpGet("{id}")]
    public async Task<IActionResult> Get(int id)
    {
        var user = await _service.GetUserAsync(id);
        return user == null ? NotFound() : Ok(user);
    }
}

12.3 Outils

NUnit
  • Framework de test mature
  • Attributs : [Test], [SetUp]
  • Assertions riches
Moq
  • Mocking d'interfaces
  • new Mock<IService>()
  • Vérification d'appels
AutoFixture
  • Génération de données de test
  • Réduit le boilerplate
  • fixture.Create<User>()
Code Coverage
  • Mesure le % de code testé
  • Coverlet, dotCover
  • Objectif : 70-80%
[TestFixture]
public class UserServiceTests
{
    private Mock<IUserRepository> _repoMock;
    private UserService _service;

    [SetUp]
    public void Setup()
    {
        _repoMock = new Mock<IUserRepository>();
        _service = new UserService(_repoMock.Object);
    }

    [Test]
    public async Task GetUser_ExistingId_ReturnsUser()
    {
        // Arrange
        var user = new User { Id = 1, Name = "Alice" };
        _repoMock.Setup(r => r.GetByIdAsync(1)).ReturnsAsync(user);

        // Act
        var result = await _service.GetUserAsync(1);

        // Assert
        Assert.That(result, Is.Not.Null);
        Assert.That(result.Name, Is.EqualTo("Alice"));
    }
}

🚫 26. À ne pas faire dans votre code

Les anti-patterns et erreurs courantes à éviter absolument pour un développeur professionnel :

26.1 Code & Structure

✔️ À FAIRE

  • Méthodes courtes : idéalement moins de 20 lignes
  • Responsabilité unique : une classe = une tâche
  • Noms significatifs : auto-documentés
  • Éviter le nesting profond : max 3 niveaux
  • Un statement par ligne
  • Guards clauses en début de méthode
  • Commenter le « pourquoi », pas le « quoi »

✘ À NE PAS FAIRE

  • Méthodes de 500 lignes avec 10 niveaux d'indentation
  • Classes fourre-tout (God Class) qui font tout
  • Noms obscurs : x, temp, data, manager
  • Duplication de code (violation DRY)
  • Commentaires inutiles qui répètent le code
  • Code mort commenté qui reste dans le repo
  • Magic numbers sans constantes nommées
// ❌ MAUVAIS : méthode trop longue, nesting profond, magic numbers
public void ProcessOrder(Order o)
{
    if (o != null)
    {
        if (o.Items != null)
        {
            if (o.Items.Count > 0)
            {
                if (o.Status == 2) // Que signifie 2 ?
                {
                    // 50 lignes de traitement...
                    foreach (var item in o.Items)
                    {
                        if (item.Price > 0)
                        {
                            // 30 lignes...
                        }
                    }
                }
            }
        }
    }
}

// ✅ BON : méthodes courtes, guards clauses, constantes nommées
private const int OrderStatusPaid = 2;

public void ProcessOrder(Order order)
{
    ArgumentNullException.ThrowIfNull(order);
    
    if (!order.HasItems) return;
    if (order.Status != OrderStatusPaid) return;
    
    ProcessOrderItems(order.Items);
}

private void ProcessOrderItems(IEnumerable<OrderItem> items)
{
    foreach (var item in items.Where(i => i.IsValid))
    {
        ProcessItem(item);
    }
}

26.2 Gestion des erreurs

✔️ À FAIRE

  • Attraper des exceptions spécifiques, pas Exception
  • Logger les exceptions avec contexte
  • Utiliser des exceptions custom pour le domaine
  • Valider les entrées en amont
  • Utiliser ArgumentNullException.ThrowIfNull
  • Libérer les ressources avec using

✘ À NE PAS FAIRE

  • catch (Exception) { } : avale les erreurs silencieusement
  • throw ex; : perd la stack trace (utiliser throw;)
  • Utiliser les exceptions pour le contrôle de flux
  • Exceptions vides sans logging
  • Ressources non libérées (fuites mémoire)
  • Mot de passe en clair dans le code
// ❌ MAUVAIS
try 
{ 
    var result = ProcessData();
}
catch (Exception) { } // Avale silencieusement !

try 
{ 
    DoSomething();
}
catch (Exception ex) 
{ 
    throw ex; // Perd la stack trace !
}

// ✅ BON
try 
{ 
    var result = await ProcessDataAsync();
}
catch (SqlException ex) when (ex.Number == -2)
{
    _logger.LogWarning(ex, "Timeout lors du traitement");
    throw new DataProcessingException("Le traitement a expiré", ex);
}

try 
{ 
    DoSomething();
}
catch (Exception ex) 
{ 
    _logger.LogError(ex, "Erreur lors de DoSomething");
    throw; // Préserve la stack trace
}

26.3 Async/Await

✔️ À FAIRE

  • async all the way : ne pas bloquer avec .Result ou .Wait()
  • Utiliser CancellationToken pour les opérations longues
  • ConfigureAwait(false) dans les bibliothèques
  • Retourner Task ou ValueTask
  • Nommer les méthodes async avec suffixe Async

✘ À NE PAS FAIRE

  • .Result ou .Wait() : risque de deadlock
  • async void : impossible à attendre, exceptions non capturées
  • Oublier await : l'opération s'exécute en tâche de fond
  • Mélanger sync et async sans raison
  • Créer des threads manuellement au lieu d'utiliser Task
// ❌ MAUVAIS
public void ProcessData()
{
    var result = GetDataAsync().Result; // Deadlock possible !
}

public async void FireAndForget() // Impossible à attendre
{
    await DoSomethingAsync();
}

// ✅ BON
public async Task ProcessDataAsync(CancellationToken ct = default)
{
    var result = await GetDataAsync(ct);
    // traitement...
}

26.4 Sécurité

✔️ À FAIRE

  • Requêtes paramétrées pour éviter l'injection SQL
  • Valider toutes les entrées utilisateur
  • Stocker les secrets dans Key Vault
  • Hasher les mots de passe (bcrypt, Argon2)
  • Utiliser HTTPS partout
  • Principe du moindre privilège

✘ À NE PAS FAIRE

  • Concaténer des chaînes SQL : injection SQL
  • Stocker des secrets dans appsettings.json ou Git
  • Faire confiance aux entrées client
  • Utiliser MD5/SHA1 pour les mots de passe
  • Exposer des stack traces en production
  • Désactiver la validation SSL
// ❌ MAUVAIS : injection SQL
var query = "SELECT * FROM Users WHERE Name = '" + userName + "'";

// ✅ BON : requête paramétrée
var query = "SELECT * FROM Users WHERE Name = @Name";
using var cmd = new SqlCommand(query, connection);
cmd.Parameters.AddWithValue("@Name", userName);

26.5 Performance

✔️ À FAIRE

  • Utiliser StringBuilder pour les concaténations en boucle
  • Paginer les requêtes (Skip/Take)
  • Utiliser AsNoTracking() pour les lectures EF
  • Mettre en cache les données fréquemment accédées
  • Utiliser Span<T> pour éviter les allocations

✘ À NE PAS FAIRE

  • Concaténer des strings en boucle : allocations massives
  • Requêtes N+1 : un appel par élément
  • Charger toutes les données en mémoire sans filtre
  • Appeler .ToList() trop tôt dans une requête LINQ
  • Ignorer le CancellationToken
// ❌ MAUVAIS : concaténation en boucle
string result = "";
for (int i = 0; i < 10000; i++)
{
    result += i.ToString(); // 10 000 allocations !
}

// ✅ BON : StringBuilder
var sb = new StringBuilder();
for (int i = 0; i < 10000; i++)
{
    sb.Append(i);
}
var result = sb.ToString();

// ❌ MAUVAIS : requête N+1
var orders = await _context.Orders.ToListAsync();
foreach (var order in orders)
{
    var customer = await _context.Customers.FindAsync(order.CustomerId);
}

// ✅ BON : Include / projection
var orders = await _context.Orders
    .Include(o => o.Customer)
    .ToListAsync();

26.6 Tests

✔️ À FAIRE

  • Un test = un comportement
  • Pattern AAA (Arrange, Act, Assert)
  • Noms de tests descriptifs
  • Tester les cas limites (null, vide, max)
  • Mocker les dépendances externes
  • Tests indépendants et isolés

✘ À NE PAS FAIRE

  • Tester l'implémentation plutôt que le comportement
  • Tests dépendants de l'ordre d'exécution
  • Mocker tout, même les objets simples
  • Ignorer les cas d'erreur
  • Tests lents à cause d'appels réels (DB, HTTP)
  • Assertions multiples dans un seul test
// ❌ MAUVAIS : test qui fait tout, nom obscur, dépendances réelles
[Test]
public void Test1()
{
    var service = new UserService(new SqlRepository()); // DB réelle !
    var result = service.GetUser(1);
    Assert.IsNotNull(result);
    Assert.AreEqual("Alice", result.Name);
    Assert.AreEqual(25, result.Age);
}

// ✅ BON : un comportement, nom descriptif, mock
[Test]
public async Task GetUserAsync_ExistingId_ReturnsUserWithCorrectName()
{
    // Arrange
    var mockRepo = new Mock<IUserRepository>();
    mockRepo.Setup(r => r.GetByIdAsync(1))
            .ReturnsAsync(new User { Id = 1, Name = "Alice" });
    var service = new UserService(mockRepo.Object);

    // Act
    var result = await service.GetUserAsync(1);

    // Assert
    Assert.That(result.Name, Is.EqualTo("Alice"));
}

✨ 27. Comment écrire un code propre qui vous différencie

Ce qui distingue un développeur senior d'un développeur junior, c'est la capacité à écrire du code lisible, maintenable et professionnel. Voici les pratiques qui font la différence :

27.1 Les principes fondamentaux

📖 Clarté avant intelligence

Le code doit être facile à lire et comprendre, pas clever ou obscur. Un code que vous ne comprenez pas dans 6 mois est un mauvais code.

Pourquoi ? Le code est lu 10 fois plus qu'il n'est écrit. Optimiser pour la lecture, pas pour l'écriture.

🎯 Cohérence

Suivez les conventions existantes du projet. Ne mélangez pas les styles. Utilisez des analyseurs de code (StyleCop, .NET Analyzers) pour automatiser le respect des règles.

Pourquoi ? La cohérence réduit la charge cognitive et facilite la navigation dans le code.

📛 Nommage significatif

Les noms doivent révéler l'intention. userRepository est meilleur que repo. CalculateTotalPrice() est meilleur que Calc().

Pourquoi ? Un bon nom élimine le besoin de commentaires et rend le code auto-documenté.

🔧 Une seule responsabilité

Chaque classe, méthode, module doit avoir une seule raison de changer (principe SRP de SOLID).

Pourquoi ? Facilite les tests, la maintenance et l'évolution du code.

🔄 DRY sans sur-abstraction

Don't Repeat Yourself, mais ne sur-abstrayez pas. Une abstraction prématurée est pire que la duplication.

Pourquoi ? La règle de trois : dupliquez une fois, refactorisez à la troisième occurrence.

🧪 Tests d'abord ou en parallèle

Écrivez les tests avant ou en même temps que l'implémentation (TDD). Les tests sont votre filet de sécurité.

Pourquoi ? Les tests documentent le comportement attendu et permettent de refactorer sans peur.

💬 Commentaires : le « pourquoi », pas le « quoi »

Le code dit comment. Les commentaires expliquent pourquoi. Ne commentez pas ce qui est évident.

Pourquoi ? Un commentaire qui répète le code devient obsolète et trompeur.

📦 Immutabilité par défaut

Préférez les objets immuables (record, init, readonly). L'état mutable est source de bugs.

Pourquoi ? L'immutabilité élimine les effets de bord et facilite la concurrence.

27.2 Les pratiques concrètes

Formatage & Style

  • Indentation : 4 espaces (pas de tabs)
  • Longueur de ligne : 120 caractères max
  • Une déclaration par ligne
  • Ligne vide entre les méthodes
  • Toujours utiliser des accolades, même pour une seule ligne
  • File-scoped namespaces (C# 10+)
  • Nullable activé globalement (<Nullable>enable</Nullable>)

var vs Type explicite

✔️ Utiliser var quand le type est évident

  • var user = new User();
  • var users = new List<User>();
  • var name = user.Name;
  • var stream = new MemoryStream();

✔️ Utiliser le type explicite quand c'est plus clair

  • IReadOnlyList<User> users = GetUsers();
  • decimal total = CalculateTotal();
  • IDictionary<string, object> metadata = GetMetadata();

Propriétés & Records

// Auto-property simple
public string Name { get; set; }

// Init-only (immuable après construction)
public Guid Id { get; init; }

// Required (C# 11+)
public required string Email { get; set; }

// Computed property
public string FullName => $"{FirstName} {LastName}";

// Record pour DTO (immuable, égalité structurelle)
public record UserDto(Guid Id, string Email, string Name);

// Non-destructive mutation
var updated = user with { Name = "New Name" };

Méthodes Async

// Suffixe Async
public async Task<User?> GetByIdAsync(Guid id)
{
    return await _repository.GetByIdAsync(id);
}

// Accepter CancellationToken
public async Task<IEnumerable<User>> GetAllAsync(CancellationToken ct = default)
{
    return await _context.Users.ToListAsync(ct);
}

// Retourner Task pour void async
public async Task SaveAsync(User user)
{
    await _repository.SaveAsync(user);
}

27.3 Ce qui vous différencie vraiment

🏆 1. Votre code parle avant vous

Un GitHub bien tenu avec des projets production-ready vaut plus qu'un CV. Recruteurs et interviewers regardent votre code avant de vous parler.

Ce qu'ils cherchent : commits réguliers, READMEs qui expliquent le « pourquoi », code qui reflète SOLID et Clean Architecture, issues et PRs qui montrent que vous travaillez comme une équipe pro.

🏆 2. Vous écrivez des tests, pas des excuses

Un développeur senior écrit des tests sans qu'on le lui demande. Pas 100% de couverture, mais les tests qui comptent : logique métier, cas limites, erreurs.

Pourquoi ça différencie : Les tests montrent que vous pensez à la maintenance, pas juste à « faire passer le ticket JIRA ».

🏆 3. Vous documentez vos décisions

Vous écrivez des ADR (Architecture Decision Records), des READMEs utiles, des commentaires XML sur les APIs publiques.

Pourquoi ça différencie : Un bon code sans documentation est un code qui mourra. Documenter le « pourquoi » est aussi important que le « comment ».

🏆 4. Vous faites des code reviews constructives

Vous commentez le code, pas la personne. Vous proposez des améliorations, pas des critiques. Vous automatisez les vérifications de style.

Pourquoi ça différencie : Les code reviews sont le meilleur outil de propagation des bonnes pratiques et de mentorat.

🏆 5. Vous pensez « maintenance » avant « livraison »

Vous vous demandez : « Est-ce que je comprendrai ce code dans 6 mois ? Est-ce qu'un nouveau dans l'équipe pourra le reprendre ? »

Pourquoi ça différencie : 80% du coût d'un logiciel est dans sa maintenance. Un code maintenable est un investissement, pas un coût.

🏆 6. Vous utilisez les outils à votre disposition

Analyseurs (StyleCop, .NET Analyzers), formatage automatique (EditorConfig), CI/CD qui bloque les PRs avec warnings, couverture de code.

Pourquoi ça différencie : Les outils attrapent les erreurs que les humains ratent. Un dev qui configure ses outils est un dev qui pense à l'échelle de l'équipe.
